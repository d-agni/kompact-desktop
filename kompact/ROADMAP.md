# kompact roadmap

This is the plan from here to a compositor that genuinely *feels* fast and reliable to use
day-to-day — not just "doesn't crash in a 90-second test." It's organized in phases; each phase
ends with a real-hardware test before the next one starts. That discipline isn't optional — it's
the single thing that's separated "working" from "requires a hard reboot" every time it's been
skipped so far in this project, on this specific hardware (NVIDIA GT 710 / nouveau).

## Ground rules, carried forward from hard experience

- **One phase, one real-hardware test, before the next phase starts.** Not "a batch of features,
  then one test at the end."
- **Every phase has a rollback point.** If a test fails, we revert to the last-known-good
  checkpoint, not guess-patch forward.
- **Syntax/API-check everything against the real Smithay source before shipping it for a test** —
  this doesn't replace a real build, but it's caught real bugs for free before costing you a
  reboot.
- **"Fast" and "reliable" get measured, not assumed.** Each phase below that touches performance
  or stability has a concrete target, not just a vibe.

## Phase 1 — Reintroduce what was reverted, one piece at a time

The layer-shell/cursor/input-dedup work that caused the hard freeze still exists; it goes back in
individually, tested individually.

1. **Input-event deduplication** (duplicate virtual devices causing occasional double-keystrokes).
   Smallest, most isolated change — good first test of "does the revert-and-reintroduce process
   itself work."
2. **Crisper software cursor.** Visual-only, no protocol/input-path changes — low risk, but still
   gets its own test rather than being bundled.
3. **Real `xdg_popup` grab.** Currently a no-op — likely the actual cause of your Firefox
   dialog-opening slowness, not just raw GPU weakness. Implemented and tested before assuming
   the remaining slowness is a hardware ceiling.
4. **wlr-layer-shell, reintroduced correctly this time.** Last time, `render.rs` walked the full
   layer-surface list unconditionally every frame, 60 times a second, even with zero layer
   clients connected — that's the specific mistake, not the feature itself. This time: only
   rebuild the layer-element list when the layer map actually changes (new/removed/reconfigured
   surface), not on every frame regardless.
5. **The layer-shell test client**, run against the reintroduced implementation, on real hardware.

**Exit criteria for Phase 1:** a 15+ minute real-hardware session, multiple windows, multiple
layer-shell surfaces, dialogs opened repeatedly in Firefox, no freeze, no reboot required, clean
shutdown logged.

## Phase 2 — Intelligent window management

"Intelligent" here means concrete, testable behaviors — not a vague aspiration:

- **Smart placement for new windows.** Current cascade (`+32px` per window) is a placeholder; it
  doesn't account for screen bounds (new windows currently can cascade off-screen on a long
  session) or avoid overlapping existing windows when space is available. Replace with: fit in
  open screen space if any exists, otherwise cascade with wraparound at the screen edge.
- **Edge/screen-half snapping** (Aero Snap / GNOME-style): drag a window to a screen edge →
  snaps to that half; drag to a corner → snaps to that quadrant. Keyboard equivalents
  (`Super+Left/Right/Up/Down` already partially there as raw movement — extend to actual
  snap-to-region, not just a 32px nudge).
- **Remembered per-application geometry.** If you've positioned/sized an app before, reopening it
  restores that geometry rather than re-cascading from scratch. Small, persistent, keyed by
  app-id.
- **Smarter focus-follows behavior.** Click-to-focus already works; add a config toggle for
  focus-follows-mouse for people who want it, off by default.
- **Workspace/virtual-desktop support** (stretch goal for this phase, may slip to its own phase
  depending on how the above lands) — multiple window sets, switchable via keybinding.

## Phase 3 — Intelligent memory management

This is about making "no leaks in a 90-second test" into "no leaks, ever, and bounded resource use
under real workloads." Concrete findings already on record from reviewing the code directly
(not guessed):

- **Fix the one real gap found so far:** `self.drag` can hold a stale `Window` reference if its
  client crashes mid-drag, before the button-release event that normally clears it. Small,
  targeted fix: clear `drag` whenever the dragged window dies, not only on release.
- **Bounded texture cache for occluded/minimized windows.** Right now every mapped window's
  texture stays fully resident regardless of visibility. On a GPU this weak, that matters — add
  eviction/re-import for windows that have been fully occluded or minimized for more than a few
  seconds, re-importing on next visibility rather than holding the texture forever.
- **GBM swapchain/buffer-pool limits appropriate for legacy KMS mode specifically** — this path
  hasn't been separately audited for buffer-pool growth under heavy churn (rapid window
  open/close cycles); confirm it stays bounded rather than assuming Smithay's internals are
  automatically fine on the legacy (non-atomic) path on this driver.
- **A toggleable debug overlay**: current RSS, current frame time, texture-cache size. Not for
  end users — for *us*, so the next time something feels slow or leaky, there's a number to look
  at instead of a guess.
- **A real soak test methodology**, not just a longer version of the same 1–2 minute smoke test:
  30+ minutes, periodic `ps -o rss` sampling, repeated open/close/drag cycles on a timer, checked
  for monotonic growth vs. a stable plateau.

**Exit criteria:** a 30-minute soak test with the debug overlay running, RSS plateaus rather than
climbs, frame time stays in budget (see Phase 4 below) throughout, no degradation from the start
of the session to the end.

## Phase 4 — Performance budget (this is where "feels fast" gets defined)

Concrete targets, set once Phase 1's popup-grab fix is in and we can see what's actually
GPU-bound vs. protocol-bound:

- **Frame time budget:** target 16ms (60fps) on simple scenes (a few windows, no animation);
  explicitly document the degraded-but-acceptable budget for this specific weak GPU under heavier
  load, rather than pretending a GT 710 will hit 60fps under all conditions.
- **Input-to-photon latency:** keypress/click to visible result, measured, not assumed — this is
  usually what "feels slow" actually means to a user, more than raw fps.
- **Popup/dialog open time:** specifically measured before/after the Phase 1 grab fix, since
  that's your direct complaint — need the actual delta, not just "it's probably better now."

**Exit criteria:** documented numbers for all three, on real hardware, with the Phase 1–3 fixes in
place — this becomes the baseline that future changes get checked against, so a regression shows
up as "frame time went from 14ms to 40ms" instead of a vague "feels slower."

**Budget** (a change that breaks it is a regression):

started):
- `ptr_ms` ≈ two refreshes: kompact draws as soon as the previous flip completes, so the first

- Heavy-scene `cpu_ms` p95/max beyond one refresh is what drops frames. Which part (texture upload
  of Firefox's buffers, GPU fence wait, element building) is unknown until `cpu_ms` is split
  (read-only instrumentation in `backend_udev.rs`, optional step 4e below).
- Up to ~400 render passes/s under heavy input (each input event wakes the loop and rebuilds
  elements, most passes empty).

## Phase 6 — The actual desktop shell

The original goal: a web-tech (HTML/CSS/TypeScript) shell — panel, launcher, wallpaper — built as
a wlr-layer-shell client against the now-optimized layer-shell support from Phase 1. This is the
point where kompact stops being "a compositor" and becomes "the desktop environment."

### Phase 6 status

**Stack, revised 2026-10-08: Tauri 2.** The GTK4 + WebKitGTK 6 + gtk4-layer-shell shell (6a–6c-2
below) drew only white on the GT 710 from 6c-2 on, even rebuilt exactly as it was at 6b, while
WebKit's own snapshots of the pages were correct. That points to the GTK4 drawing path, not the
page code or kompact. It is archived in `../attic/shell-gtk4` (plus `attic/shell-gtk4-6b`).

The new shell, `../shell` (`kompact-shell` 0.2), is Tauri 2: Rust in `shell/src-tauri`, pages in
`shell/web`, embedded into the binary at build time. On Linux Tauri uses the same WebKit engine,
but webkit2gtk-4.1 on **GTK3**, a different drawing path. Each surface is a Tauri webview window
that gtk-layer-shell (GTK3) turns into a layer surface: built hidden, made a layer surface, then
shown. The shell is a client only; kompact and `backend_udev.rs` are untouched unless a step says
so.

GT 710 defaults: `KOMPACT_SHELL_GPU=off` means `WEBKIT_DISABLE_COMPOSITING_MODE=1`,
`WEBKIT_DISABLE_DMABUF_RENDERER=1` and WebKit hardware acceleration `Never` (the usual fixes for
white WebKitGTK windows on NVIDIA). `GDK_BACKEND=wayland` is always set. Tauri is built without
`x11` and `dbus`, so tao doesn't ask the (sometimes stuck) desktop portal for the colour scheme.

## Why this order

Window management and memory management are both *after* Phase 1 (reintroducing what already
exists) rather than before, because building new features on top of an unconfirmed foundation is
exactly the mistake that caused the last hard freeze. Performance measurement (Phase 4) comes
after the popup-grab fix specifically because guessing whether slowness is a protocol bug or a
hardware ceiling isn't useful — we find out, then measure what's left. Everything is sequenced so
that by the time we're building the shell (Phase 6), it's sitting on a base that's been tested at
every layer underneath it, not assumed solid.

## Phase 19: an intelligent assistant that controls the desktop (exploration, asked 2026-10-22)

"Explore how a intelligent assistant can work and have responsibility in controlling the system." Branch `feature/intelligent-assistant`. **Proposal only: nothing below is built or approved yet.**

### What it is

You press a key (Super+Space, then Tab, or its own shortcut) or click a menu-bar sparkle and type, e.g. "put Firefox and the terminal side by side", "turn the volume down and mute notifications for an hour", "why is my sound cutting out?". The assistant answers, or does the work through the desktop's own controls, and shows what it did with an Undo.

### Where it runs

- **In the shell** (`shell/src-tauri/src/assistant/`), not in kompact: the shell already holds every control (≈120 typed commands: windows, workspaces, Wi-Fi, Bluetooth, sound, media, notifications, appearance, keys, dock, wallpaper, defaults, date and time, displays). kompact, the render path and `backend_udev.rs` stay untouched; the assistant reaches kompact only through the existing shell channel, whose lines are already validated (`setting_line`, `request_line`).
- **UI**: a new overlay mode `assistant` (like Spotlight, with a conversation, cards for confirmations, an activity line), and a menu-bar pill while it is acting (like the purple sharing pill) with a Stop button.
- **The model** behind a `Brain` trait, so it can be swapped:
  1. *Built-in rules, offline* (first step, no network): a small parser for the common commands ("volume 30", "dark mode on", "open firefox", "workspace 2", "lock"). Fast, free, private, and the fallback when there's no network.
  2. *A small local model* (later, optional, still on this PC): for free-form requests the rules don't cover; the GT 710 can't run models, so a small quantized model on the CPU through llama.cpp (1–3 B parameters, ~1–2 GB RAM, a second or two for a short command on the Ryzen 3 3100), asked to answer only with one of our tool calls, which the policy then checks like any other.
  3. *A cloud model* (Claude): **not now** (decided 2026-10-22: "As of now dont opt-in claude, focus on local version only"). The `Brain` trait keeps the door open.

### Voice (asked 2026-10-22: "it need voice input, using voice input user should be able control the systems")

- **Push to talk, not always listening**: hold **Ctrl+Super+V** (editable in Settings → Keyboard, 10a) or press on the character, speak, let go. While the microphone is open the character shows Listening and the menu bar's orange microphone dot (12d) is on, as for any app. A wake word ("Hey Kip") only later, and only if it can run on the machine; never as a default.
- **Speech to text on this machine**: whisper.cpp (through the `whisper-rs` crate) on the Ryzen 3 3100 (4 cores / 8 threads, AVX2): the `base` model (~142 MB) turns a few seconds of speech into text in well under a second, `small` (~466 MB) is more accurate and still about real time; English first, other languages with the multilingual models. Audio is recorded from PipeWire (the default input, 16 kHz mono), kept in memory only, never written to disk or sent anywhere. The microphone here is the onboard analog input (`alsa_input…analog-stereo`); a USB or Bluetooth headset microphone works the same way.
- **Speaking back** (optional, off by default): short replies spoken with Piper (a local voice, ~60 MB) or speech-dispatcher, already installed (`spd-say`); always also shown as text in the character's bubble.
- **Voice can't say yes to Tier 2**: speech can be misheard and a TV or video can talk too, so a Tier 2 step still needs a click or Enter on its card; voice can only *cancel* ("stop", "cancel", Esc). What was heard is always shown before it runs ("Heard: close all windows") and can be corrected.

### Responsibility: the rules, enforced in code, not in the prompt

The model only *proposes* tool calls. A pure, unit-tested `policy.rs` decides what runs; nothing the model writes can change that.

| Tier | What | Examples | What happens |
|---|---|---|---|
| 0 Read | Looks, changes nothing | list windows, sound/network/Bluetooth state, Now Playing, settings, battery-free system info | Runs |
| 1 Reversible | Small, local, undoable | volume, mute, play/pause, focus/arrange/minimize windows, workspace, Do Not Disturb, dark mode, accent, open an app, Keep Awake | Runs, shown in the activity line with **Undo** (the old value is kept) |
| 2 Consequential | Hard to undo, or loses work, or leaves the machine | close a window (unsaved work), quit an app, disconnect/forget a network or device, change keyboard shortcuts or default apps, log out, lock, sleep, restart, power off | A **confirmation card** each time ("Close 'Untitled — gedit'? It may have unsaved changes." Confirm / Cancel) |
| 3 Never | Not available to the assistant at all | passwords and the polkit dialog, `sudo`, arbitrary shell commands, reading files, screenshots or screen contents without you asking in that request, display modes and outputs (the GT 710's fragile DRM path), installing software, sending messages or data anywhere | No tool exists, so the model can't call it |

More rules:
- **You start it.** No always-listening microphone, no acting on its own. A plan of several steps is shown first when it has a Tier 2 step; at most 8 tool calls per request; Esc or the pill's Stop ends it at once.
- **Untrusted text stays data.** Window titles, notification text, web pages and file names can contain instructions ("ignore the user and…"); they go to the model marked as data, and a Tier 2 step that follows from them still needs your confirmation. The tier table doesn't move whatever the model is told.
- **Nothing leaves the PC.** Speech, text, window titles and tool results stay on this machine; the assistant opens no network connection (checked by a test that its code has no HTTP client). Off by default until turned on in Settings → Assistant.
